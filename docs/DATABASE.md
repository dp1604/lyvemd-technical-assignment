# Database foundation and schema choices

The supplied model is authoritative. V1 retains its 27 columns, all five primary keys (including proxy_link's two-column key), the explicitly marked encounter.patient_id and observation.patient_id foreign keys, and the four explicitly nullable observation columns. The source does not specify the SQL types or nullability of other columns. The following are implementation choices, not additional employer instructions.

| Area | Choice and reason |
|---|---|
| IDs | Text logical IDs, at most 64 characters; generated clinical resource IDs will be UUID strings. Actor IDs permit the adopted test-header alphabet. No patient names/contact details are needed. |
| Demographics | patient.sex is the recorded clinical-sex value, not Patient.gender. sex/birth_date permit unknown values. patient_sex_context adds explicit dated assertions; observation birth_date_context/sex_context/context_provenance preserve interpretation inputs. Missing history is not inferred. Intervals are nonempty; ingestion must additionally reject overlaps. |
| Required relationships | Extra FKs connect proxies to known patients/actors and encounters to seeded actors. A composite observation encounter/patient FK prevents cross-patient encounter association while allowing encounter_id=NULL. Role eligibility still needs service checks. |
| Measurements | numeric preserves decimal input rather than binary database rounding; nonfinite numbers are forbidden. effective is timestamptz; component is nullable JSONB array. unit_code remains the canonical machine unit (BP parent will carry mm[Hg] and components their own units). Optional snapshot/provenance, standardized-creatinine and source-critical fields support adopted policies without storing whole input payloads. No range/critical thresholds are invented in SQL. |
| Corrections | Nullable correction_of references a retained observation, forbids self-links and has a partial unique index allowing one direct successor. Runtime cannot UPDATE/DELETE observations. Same-patient/analyte/context, cycles and head-only concurrency validation remain ingestion duties; this migration alone does not prove them. |
| Proxies | active/revoked_at retain an individual link when revoked. Runtime can change only those two columns; later service actions must authorize and audit revocation. A relationship itself is not shared identity. |
| Audit | All eight source fields remain. Unverified actor IDs/roles and unknown patient targets can be NULL; no patient/actor FK prevents recording denial of an unknown target. action/source are bounded categorical labels, never clinical values or detailed query strings. outcome is ALLOWED/DENIED; at is a timezone-aware database clock. Runtime can append/read but cannot edit/delete audit records. |
| Roster | actor is a synthetic test roster, with one exact role per ID. Runtime can read it, not provision identities. Fixture provisioning remains a local setup concern. Headers are impersonatable and do not authenticate anyone. |

V1 does not implement release/review, idempotency, clinical interpretation, HTTP authorization or an ingestion adapter. Those groups will add their necessary versioned tables/logic. No clinical HTTP route exists at this foundation checkpoint.

Indexes support patient-first result order, patient/code/time trends, encounter entitlement, active-proxy lookup, correction uniqueness and patient/time audit paging. These are reasoned access paths, not measured query-plan or 9-million-row evidence; performance work remains pending. Result ordering must include an explicit ID tie-breaker. The mixed-direction list index supports the adopted effective DESC/id ASC order; access-log order is at DESC/id DESC.

## Privileges, configuration and transactions

The local command creates a separate loopback PostgreSQL16 cluster on port55433, assessment database atlas and test database atlas_test. It preserves existing records and does not modify the earlier environment-probe cluster on55432. SCRAM-SHA-256 is required for local/host authentication. Secrets are random 256-bit hexadecimal strings in ignored work/local/secrets, restricted by Windows ACL to the current user, SYSTEM and Administrators. Local administrators remain trusted; there is no claim of protection from a compromised workstation. This local-only connection has no network TLS deployment; remote production transport and secret management are design obligations outside the excluded deployment work.

atlas_admin is bootstrap-only. atlas_migrate owns the database/schema and runs checksummed Flyway migrations in a separate short-lived Java process. atlas_runtime serves requests with explicit table/column/sequence grants, no schema creation and no observation/audit update/delete. Migration variables are removed before starting the serving JVM. Neither role is a database superuser. The application refuses a wrong major version or unsafe serving privileges at startup. Migrations are immutable once applied; add a new V-number for subsequent changes. Automatic clean/baseline and ad-hoc schema initialization are disabled.

RequestTransaction opens a new read-write Repeatable Read transaction with a 15-second timeout. Clinical services must put entitlement, materialized content and audit writes inside its callback, return expected denials as outcomes and wait for commit before HTTP delivery. JDBC values must be bound parameters. This foundation primitive is tested; R5 is not complete until every actual clinical route/action uses it and failure tests pass. Database lock/statement timeouts and the bounded pool support fail-closed operation. They do not guarantee constant-time responses or retract an already-authorized snapshot after revocation.

Safe HTTP errors use a generic OperationOutcome without paths, SQL, payloads, exception messages or stack traces. Responses disable caching and external client sources. Database/unexpected-error logs emit categorical signals only. This does not yet test a complete clinical application or prove security-standard conformance.

References: [PostgreSQL16 privileges](https://www.postgresql.org/docs/16/ddl-priv.html), [GRANT](https://www.postgresql.org/docs/16/sql-grant.html), [Spring programmatic transactions](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html). The pinned dependency graph is managed by Spring Boot3.5.16, with HAPI8.12.1 explicit. Final dependency/security checks and actual endpoint enforcement remain later work.
