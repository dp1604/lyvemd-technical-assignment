# Database foundation and schema choices

The supplied model is authoritative. V1 retains its 27 columns, all five primary keys (including proxy_link's two-column key), the explicitly marked encounter.patient_id and observation.patient_id foreign keys, and the four explicitly nullable observation columns. The source does not specify the SQL types or nullability of other columns. The following are implementation choices, not additional employer instructions.

| Area | Choice and reason |
|---|---|
| IDs | Text logical IDs, at most 64 characters; generated clinical resource IDs will be UUID strings. Actor IDs permit the adopted test-header alphabet. No patient names/contact details are needed. |
| Demographics | patient.sex is the recorded clinical-sex value, not Patient.gender. sex/birth_date permit unknown values. patient_sex_context adds explicit dated assertions; observation birth_date_context/sex_context/context_provenance preserve interpretation inputs. Missing history is not inferred. Intervals are nonempty; ingestion must additionally reject overlaps. |
| Required relationships | Extra FKs connect proxies to known patients/actors and encounters to seeded actors. A composite observation encounter/patient FK prevents cross-patient encounter association while allowing encounter_id=NULL. Role eligibility still needs service checks. |
| Measurements | Task code `2947-0` follows the disclosed [D-17 synthetic assessment convention](DECISIONS.md); it is not a verified production potassium mapping. numeric preserves decimal input rather than binary database rounding; nonfinite numbers are forbidden. effective is timestamptz; component is nullable JSONB array. unit_code remains the canonical machine unit (BP parent will carry mm[Hg] and components their own units). Optional snapshot/provenance, standardized-creatinine and source-critical fields support adopted policies without storing whole input payloads. No range/critical thresholds are invented in SQL. |
| Corrections | Nullable correction_of references a retained observation, forbids self-links and has a partial unique index allowing one direct successor. Runtime cannot UPDATE/DELETE observations. Same-patient/analyte/context, cycles and head-only concurrency validation remain ingestion duties; this migration alone does not prove them. |
| Proxies | active/revoked_at retain an individual link when revoked. V3 adds first revoked_by attribution; runtime may change only those link-state columns. The patient-self local service authorizes and audits individual revocation; it exposes no reinstatement command. A relationship itself is not shared identity. |
| Audit | All eight source fields remain. Unverified actor IDs/roles and unknown patient targets can be NULL; no patient/actor FK prevents recording denial of an unknown target. action/source are bounded categorical labels, never clinical values or detailed query strings. outcome is ALLOWED/DENIED; at is a timezone-aware database clock. Runtime can append/read but cannot edit/delete audit records. |
| Roster | actor is a synthetic test roster, with one exact role per ID. Runtime can read it, not provision identities. Fixture provisioning remains a local setup concern. Headers are impersonatable and do not authenticate anyone. |

V2 adds immutable completed ingestion receipts, held review state, actor-roster audit classification, demographic/interpretation provenance and exact submicrosecond time preservation. Runtime receives SELECT/INSERT on the new tables; no clinical/audit UPDATE/DELETE is granted. V3 adds narrow review-metadata UPDATE grants and dedicated audit target_proxy_id, plus the actual [local workflow](WORKFLOW.md); source/audit UPDATE/DELETE remains forbidden. Source columns and meanings stay intact. See [verification](VERIFICATION.md).

Indexes support patient-first result order, patient/code/time trends, encounter entitlement, active-proxy lookup, correction uniqueness and patient/time audit paging. Actual small-cohort measurements and six non-ANALYZE plans are recorded in [PERFORMANCE](PERFORMANCE.md); they do not establish 9-million-row capacity or executed SQL timings. Result ordering must include an explicit ID tie-breaker. V2 replaces the original patient/time indexes with exact-time indexes including effective_submicro_nanos: list effective DESC/residual DESC/id ASC; trend effective ASC/residual ASC/id ASC. Access-log order is at DESC/id DESC. The list/trend services explicitly sort after visible-series graph processing.

## Privileges, configuration and transactions

The local command creates a separate loopback PostgreSQL16 cluster on port55433, assessment database atlas and test database atlas_test. It preserves existing records and does not modify the earlier environment-probe cluster on55432. SCRAM-SHA-256 is required for local/host authentication. Secrets are random 256-bit hexadecimal strings in ignored work/local/secrets, restricted by Windows ACL to the current user, SYSTEM and Administrators. Local administrators remain trusted; there is no claim of protection from a compromised workstation. This local-only connection has no network TLS deployment; remote production transport and secret management are design obligations outside the excluded deployment work.

atlas_admin is bootstrap-only. atlas_migrate owns the database/schema and runs checksummed Flyway migrations in a separate short-lived Java process. atlas_runtime serves requests with explicit table/column/sequence grants, no schema creation and no observation/audit update/delete. Migration variables are removed before starting the serving JVM. Neither role is a database superuser. The application refuses a wrong major version or unsafe serving privileges at startup. Migrations are immutable once applied; add a new V-number for subsequent changes. Automatic clean/baseline and ad-hoc schema initialization are disabled.

RequestTransaction opens a new read-write Repeatable Read transaction with a 15-second timeout. Clinical services must put entitlement, materialized content and audit writes inside its callback, return expected denials as outcomes and wait for commit before HTTP delivery. JDBC values must be bound parameters. Every actual GET and local workflow action uses this boundary; [Verification](VERIFICATION.md) verifies success/denial and insert/deferred-commit audit faults. Database lock/statement timeouts and the bounded pool support fail-closed operation. They do not guarantee constant-time responses or retract an already-authorized snapshot after revocation.

Local structural HAPI validation and strict parsing use only caller bytes and bundled definitions before a database transaction opens. The cooperative 45-second preparation budget is checked between/after entries; it cannot interrupt an individual validator call. All stored roster, receipt, authorization/reference reads, clinical planning, inserts and audit remain inside one fresh 15-second Repeatable Read action. Prepared checks can be reused across retries; roster and durable receipt precedence are rechecked before publishing a prepared failure. Existing exact receipts can replay during validator unavailability; new requests receive audited 503 with no completed receipt. See [ingestion contract](FHIR_INGESTION.md).

The short-lived fixture code writes only synthetic roster actors and receipt-verified individual proxy links in the designated local databases. Its non-superuser schema-owner role is privileged; the code boundary is not a claim that that role lacks other schema permissions. It does not write clinical, review, receipt or audit records, overwrite roles or reactivate revoked links. HTTP creates clinical sources; the actual runtime workflow controls review/release. Serving and non-web runtime contexts have owner credentials removed. See [dataset evidence](VERIFICATION.md).

Safe HTTP errors use a generic OperationOutcome without paths, SQL, payloads, exception messages or stack traces. Responses disable caching and external client sources. Database/unexpected-error logs emit categorical signals only. The actual regression is recorded in [verification](VERIFICATION.md); no security-standard conformance is claimed.

References: [PostgreSQL16 privileges](https://www.postgresql.org/docs/16/ddl-priv.html), [GRANT](https://www.postgresql.org/docs/16/sql-grant.html), [Spring programmatic transactions](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html). The pinned dependency graph is managed by Spring Boot3.5.16, with HAPI8.12.1 explicit. Endpoint regression and personal review have their stated scopes in [verification](VERIFICATION.md).

Current historical-context ingestion is create-only: assertions for a fresh server-assigned patient are validated together and inserted in that action. There is no existing-patient demographic editing API or concurrent interval-append path, so the old V1 comment about a patient ingestion lock describes an earlier intent, not an implemented independent patient lock. Existing patient context is read under the request snapshot. Future interval editing needs its own concurrency policy. The shared detail view's materialization and timing limits are in [RESULT_VISIBILITY](RESULT_VISIBILITY.md).
